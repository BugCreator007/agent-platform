## 3. 现状核对（代码事实）

以下事实决定了本轮不是「改造已有功能」，而是「补三类基础设施 + 修一个安全问题」：

1. `chat_sessions` 表没有 `user_id`（[V1__init.sql](../../backend/src/main/resources/db/migration/V1__init.sql)），所有会话全局共享。
2. 管理端会话消息接口只要求登录、不校验归属（[SessionController.java](../../backend/src/main/java/com/agentplatform/modules/chat/interfaces/rest/SessionController.java)），任何已登录账号都能按 ID 读取他人会话，**存在越权读取风险**。
3. 用户端会话快照存在浏览器 `localStorage`，按「用户名 + 智能体」隔离（[user-web/src/App.tsx](../../user-web/src/App.tsx)），换设备、换浏览器即丢失，也没有服务端会话列表。
4. 平台没有消息级反馈表，也没有产品事件表；`usage_records` 只有建表语句，代码中没有任何写入（`grep UsageRecord` 无业务引用）。
5. 运营概览的会话指标来自 `chat_sessions` 汇总，能回答「有多少会话」，不能回答「会话有没有用」；评测与成本仍是演示数据。
6. `open` 模块只有包占位，`api_keys` 只能管理不能用于鉴权；模板中心不存在。

结论：A1 必须顺带修复会话归属与越权读取；B0 需要新建事件表并明确事件口径；B1/B2 需要新建反馈与洞察读模型。

### 4.2 开发建议默认口径（技术评审会复核）

以下问题不影响架构选型，开发先按默认执行；产品/测试在技术评审会上如无异议即视为确认。

| 编号 | 待确认项 | 建议默认 | 理由 |
|---|---|---|---|
| Q5 | 负反馈原因标签 | 六类：答非所问 / 信息有误 / 内容不完整 / 信息过时 / 不安全或冒犯 / 其他 | 覆盖主流 bad case 分类，可扩展；标签编码入库，文案可配置 |
| Q6 | 会话删除语义 | 用户侧软删除：列表不可见、不可恢复；管理员仍可在运行追踪中按需查看 | 保留审计与洞察事实；避免事件与反馈悬挂 |
| Q7 | 会话标题规则 | 默认取首条用户问题前 30 字；用户重命名后不再自动覆盖 | 兼顾可读性与用户控制 |
| Q8 | 洞察统计窗口 | 默认近 7 天，可选 30 天，最大 90 天；按 Asia/Shanghai 展示 | 与现有会话统计口径一致，避免全表扫描 |
| Q9 | 历史会话（无 `user_id`） | 不迁移给任何用户；用户端不可见，管理端可见 | 无法可靠判断归属，强行归属会制造越权 |
| Q10 | VIEWER 角色权限 | 管理端会话/反馈/洞察仅 PLATFORM_ADMIN、DEVELOPER 可见；VIEWER 只能看自己的会话 | 反馈与洞察含用户原文，收紧到最小可见范围 |
| Q11 | 空会话 | 进入聊天页不落库；发送首条消息才创建会话；「新建会话」为前端清空当前上下文 | 避免列表被空会话污染，行为与主流 AI 产品一致 |
| Q12 | 反馈修改与撤回 | 同一用户对同一消息可修改或撤回；后台保留 `feedback_submitted` 事件用于审计 | 用户可能误点；事件与状态分离，洞察以当前状态为准 |
| Q13 | 埋点是否记录问题原文 | 事件 properties 不记录原文，只记 ID、长度、耗时、条数；原文只存在 `session_messages` | 降低事件表隐私面，原文仍可从消息表按权限读取 |
| Q14 | 防重复反馈 | 同一 `message_id + user_id` 唯一，重复提交做更新而非新增 | 防止刷量，保证统计准确 |

## 5. 需求拆解与验收标准

### 5.1 PRD-A1 用户端会话管理

**用户故事**：作为已登录用户，我想看到自己与各智能体的历史会话，并能重命名、删除、跨设备继续聊，以便把事办完而不是每次从零开始。

**范围**
- 用户端会话侧边栏：当前用户会话列表，按最近活跃倒序，支持按智能体筛选与分页。
- 重命名：1–60 字，保存后列表与聊天页标题同步。
- 删除：二次确认；删除后列表消失，服务端软删除。
- 续聊：打开历史会话加载消息并继续对话；刷新/换设备不丢失。
- 归属校验：任何会话读取、续聊、重命名、删除、反馈都必须校验当前用户是会话所有者。

**不做**
- 终端用户注册、邀请、部门与租户（P1-8）。
- 会话分享、导出、跨用户协作。
- 空会话创建与草稿保存。

**验收标准**
1. 两个账号 A/B 各自登录，A 看不到 B 的会话；A 用 B 的会话 ID 调消息/续聊/重命名/删除接口均返回 404。
2. 发送首条消息后会话出现在列表，标题为首问前 30 字；刷新浏览器、换浏览器登录后列表与消息一致。
3. 重命名后列表、聊天页标题同步，刷新后保留；空标题或超过 60 字被拒绝。
4. 删除后列表消失，直接访问旧会话 URL/ID 返回 404；管理端仍能查到该会话（软删除标记）。
5. 会话列表支持按智能体筛选，分页参数非法时返回 400。

### 5.2 PRD-B0 产品埋点基线

**用户故事**：作为平台运营者，我想知道用户从打开智能体到得到答案、再到采纳或放弃的完整路径，以便判断平台是否真的在交付价值。

**范围**
- 服务端事件：`session_started`、`message_sent`、`answer_completed`、`answer_failed`、`feedback_submitted`、`session_deleted`。
- 客户端事件（白名单）：`agent_opened`、`answer_copied`、`citation_downloaded`。
- 事件写入独立 `product_events` 表，只记 ID、长度、耗时、条数、模型等属性，不记问题原文。
- 有效会话口径：会话内用户消息 ≥ 2 条，或存在 👍，或存在复制/引用下载事件，任一成立即有效。
- 埋点失败不阻断对话主流程，记录告警日志与失败计数。

**不做**
- 第三方分析平台接入、实时流式分析、用户行为回放。
- 事件表长期归档与分区（保留策略在技术设计中说明）。

**验收标准**
1. 完成一次对话后，事件表依次出现 `session_started`、`message_sent`、`answer_completed`，会话 ID 与智能体 ID 正确。
2. 模型失败或超时出现 `answer_failed`，包含失败阶段，且用户侧错误提示不受影响。
3. 复制答案、下载引用后分别出现 `answer_copied`、`citation_downloaded`，事件归属到当前用户与会话。
4. 提交反馈出现 `feedback_submitted`，`rating`、`reasons`、`hasComment` 与提交内容一致。
5. 故意让事件写入失败（如表不存在/超长属性）时，对话仍正常完成，日志有 WARN 与失败计数。

### 5.3 PRD-B1 消息级反馈

**用户故事**：作为使用者，我想对某条回答点赞或点踩并说明原因，以便平台改进；作为运营者，我想把这些反馈聚成可处理的 bad case。

**范围**
- 助手消息下方 👍/👎；点踩后弹出六类原因多选（至少选 1 个）与选填纠错文本（≤500 字）。
- 同一用户对同一消息只能有一条反馈，可修改、可撤回；撤回后按钮恢复未反馈状态。
- 管理端 bad case 列表：按时间、智能体、原因、处理状态筛选；可查看脱敏后的问答上下文；可标记「已处理/忽略」。
- 反馈仅针对助手消息；用户消息不可反馈。

**不做**
- 自动把 bad case 转成评测用例（B3）。
- 反馈奖励、通知、用户可见的处理进度。

**验收标准**
1. 点赞/点踩后按钮状态立即更新，刷新后仍保留；同一消息重复提交只保留一条记录。
2. 点踩未选原因返回 400；纠错文本超过 500 字返回 400；对用户消息或他人消息反馈返回 404。
3. 撤回反馈后数据库记录删除或标记失效，按钮恢复；洞察不再统计该反馈。
4. 管理端可按原因与状态筛选，列表展示脱敏后的问题与回答；非管理员访问返回 403。
5. 反馈接口失败时仅提示「反馈失败，请重试」，不影响消息展示与继续对话。

### 5.4 PRD-B2 会话洞察（只读版）

**用户故事**：作为平台运营者，我想每周看到有效会话数、用户在哪一步放弃、哪些问题没被解决，以便决定下一轮补知识还是改提示词。

**范围**
- 新增管理端「反馈与洞察」页：指标卡、会话漏斗、未解决问题 Top20、高频问题 Top20、全部反馈列表。
- 指标口径：有效会话数/率、首答有用率、负反馈率、平均轮次、放弃率、失败回答数。
- 未解决问题：近窗口内 👎 且未处理/忽略的反馈，按原因标签聚合，展示脱敏问题与回答摘要。
- 高频问题：按会话首问归一化后计数，展示出现次数与负反馈次数。
- 只读：不做主题聚类、不做 bad case 转评测、不做知识缺口建议（B3/B4）。

**不做**
- AI 自动聚类与摘要（依赖真实评测与额外模型成本）。
- 导出用户原文（隐私约束）。

**验收标准**
1. 指标卡与漏斗在近 7 天演示数据下数值可解释；切换 30 天窗口数值随之变化。
2. 未解决问题列表只包含 👎 且状态为 open 的反馈，原因筛选正确；问题与回答文本中的手机号、证件号已脱敏。
3. 高频问题按归一化文本聚合，标点/空格差异不产生重复条目。
4. 非 PLATFORM_ADMIN/DEVELOPER 访问洞察接口返回 403；窗口超过 90 天返回 400。
5. 无数据时页面展示空状态，不出现 NaN、除零或 500。

## 6. 需求对齐结论

1. **范围**：A1、B0、B1、B2 四项为一个完整闭环（会话 → 对话 → 反馈 → 洞察），本轮一起交付；C1、E3 明确顺延。
2. **身份**：复用现有平台账号；本轮只补会话归属与越权校验，不新建终端用户体系。
3. **隐私**：原文落库、仅管理员可见、接口展示脱敏；事件表不记原文。
4. **指标**：有效会话 = 追问 / 点赞 / 复制 / 引用下载任一；具体公式见技术设计第 10 节。
5. **依赖**：真实评测（P1-6）与真实成本（P1-5）不在本轮，洞察页不展示评测分与成本结论，避免继续放大演示数据的可信度问题。
6. **验收**：产品按第 5 节验收标准验收；测试按技术设计第 14 节测试矩阵执行；两者冲突时以本记录为准并回写文档。

## 7. 风险与产品侧提醒

| 风险 | 影响 | 应对 |
|---|---|---|
| 历史会话无归属，上线后用户端看不到旧对话 | 用户体验断层 | 上线公告说明；如需保留，由管理员按工单手工归属，本轮不做自动迁移 |
| 反馈与洞察含用户原文，存在隐私合规风险 | 信任与合规 | 仅管理员/开发者可见；接口脱敏；事件不记原文；后续补留存期与导出审计 |
| VIEWER 权限收紧，管理端运行追踪对 viewer 只剩自己的会话 | 演示账号体验变化 | 产品确认演示脚本改用 admin/developer；VIEWER 仍可用于用户端演示 |
| 「采纳」依赖前端事件，埋点丢失会低估有效会话 | 指标偏低 | 复制/下载失败不影响主流程；洞察页注明口径；后续可通过后端导出行为补强 |
| 本轮不接真实评测与成本 | 洞察无法回答「版本变好没有」 | 产品明确本轮只回答「用没用、哪里没用」；版本对比留到下一轮 |
