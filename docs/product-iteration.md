# Agent 平台产品迭代思考

> 角色：本项目的产品负责人（Claude 担任），负责新需求定义、迭代主题规划与验收标准。
> 更新：2026-11-17 · 依据：`README.md`、`docs/implementation-status.md`、`docs/backlog.md` 与代码现状。
> 使用方式：每轮迭代开始前更新一次；需求编号 `PRD-xx` 可在工程 backlog 中引用。

## 0. 一轮迭代怎么走

1. 看数据与反馈：周会话量、有效会话率、负反馈、未解决问题 Top10。
2. 选一个主题（下面第 4 节），只选一个，其余进候选池。
3. 产出 3–5 张需求卡：背景 / 用户故事 / 方案要点 / 验收标准 / 埋点 / 风险。
4. 工程侧按 `docs/backlog.md` 的 P0→P1 消化；产品侧保证每轮至少有一个**用户可感知**的变化。
5. 下一轮复盘时，用同一组指标回答"这次改动有没有用"。

## 1. 产品定位（已确认：两者兼顾）

一句话：**企业内部的 AI 应用工厂**——构建者在这里把业务知识做成智能体和流程，业务人员在门户或工作软件里直接使用，平台负责知识、工具、权限、评测、成本与审计。

三类用户与各自的核心诉求：

| 角色 | 是谁 | 要什么 | 现在的痛点 |
|---|---|---|---|
| 构建者 | 开发者、业务 BP | 低成本做出可用的智能体 | 能力多但每个都浅；调效果靠感觉，没有对比与回归 |
| 运营者 | 平台管理员、业务负责人 | 看得见效果、控得住成本和风险 | 没有反馈闭环，评测/成本是演示数据，无法证明价值 |
| 使用者 | 一线员工、外部客户 | 在熟悉的地方把事办完 | 只有"目录 + 聊天"，离开门户就用不了；没有历史、不能分享 |

定位已确认按"两者兼顾"执行：用真实产品的标准设计，但每轮迭代保证一条完整、可演示、可讲述的业务闭环。取舍时，先保证闭环完整，再追求能力广度。

## 2. 北极星与护栏指标

- **北极星：周有效会话数**。有效 = 用户追问、采纳、正向反馈或完成任务中的任意一种；纯打开不提问不算。
- 过程指标：智能体覆盖部门/场景数、首答有用率、平均解决轮次、7 日留存、人均周会话。
- 护栏指标：单会话成本、P95 首字延迟、负反馈率、越权/审计异常数。
- 当前缺口：平台有 Prometheus 技术指标，但没有**产品埋点**（会话漏斗、有效会话、反馈、放弃），所以第 5 节把"埋点基线"列为前置。

## 3. 现状判断（PM 视角）

能力面已经很宽：13 个管理模块 + 用户门户，覆盖构建、评测、发布、运维全流程。但产品上有三个结构性缺口：

1. **深度不足，演示態多**：评测是随机分、成本是静态数据、部分工具是模拟实现。功能"能看不能用"会直接伤害平台可信度。
2. **闭环缺失**：用户反馈 → bad case → 评测集 → 版本对比 → 再次发布，这条最能体现 AI 产品方法论的主链路，目前没有产品载体；知识库也没有"问题问了但没检索到"的回收机制。
3. **使用场景太薄**：用户端只有"智能体目录 + 单会话聊天"，没有多会话历史、反馈、分享、主动推送；没有开放 API / 嵌入 / IM 渠道，用户离开门户就断了。

一句话总结：**现在是一台能力展示机，还不是一台价值交付机。**

## 3.5 首个场景（已确认）：内部知识问答

**场景定义**：员工在内部门户提问公司制度、业务流程、技术规范，答案必须带可核验的原文引用；没有可靠答案时明确说"不知道"并留下缺口，而不是编造。

三个角色与任务：

- **提问员工**：快速拿到可信答案，能点开原文核实，找不到上次问答时能翻历史。
- **知识运营**（HR / 财务 / 技术文档负责人）：知道哪些问题没人答上来、该补哪一篇文档，补完后能看到同类问题变少。
- **平台管理员**：控制谁能看哪些文档，掌握质量与成本。

判断这个场景做得好不好的指标（埋点上线后取数）：

- 有效回答率：有引用且未收到负反馈的问答会话 / 总问答会话
- 无答案率与误拒率（该答的没答、不该答的硬答）
- 答案采纳率：点赞 / 有反馈会话
- 知识缺口关闭数：补文档后同类问题不再出现的数量
- 检索质量：金标集上的 Recall@10、nDCG@10
- 首答延迟、单次问答成本

核心闭环与当前断点：

```text
提问 → 检索 + 引用回答 → 反馈 / 无答案 → 缺口聚类
     → 补文档 / 改分块 / 调阈值 → 评测回归 → 发布
```

断点：没有反馈入口、没有无答案识别与缺口回收、引用只到文档级（无位置与版本）、评测是演示分、发布页没有版本对比。

场景边界（本轮不做）：扫描件 OCR 与表格理解、跨部门知识社区、外部客户客服（转人工与工单属于另一个场景）。

## 4. 迭代主题与候选需求

### 主题 A：把一次对话变成一次交付（体验纵深）

为什么：用户不为"聊天"付费，为"把事办完"付费。

- `PRD-A1` **用户端会话管理**：会话列表、新建、重命名、删除、按智能体归档（后端会话已持久化，缺列表接口与入口）。
- `PRD-A2` **答案形态升级**：结构化卡片（订单/工单/表格）、可下载产物（报告/Excel）、关键结论高亮。
- `PRD-A3` **对话内任务**：多步骤任务进度、中间产物、失败重试；支持"重新生成 / 编辑重发"。
- `PRD-A4` **文件与多模态**：对话内直接上传图片 / Excel / PDF 做一次性分析，不进知识库。

验收参考：售后场景从提问到拿到"可直接转发"的处理结论 ≤ 3 轮。

### 主题 B：反馈闭环，让平台自己变好（运营纵深）

为什么：没有反馈的 AI 产品只能靠猜；这是平台长期价值的来源。

- `PRD-B0` **产品埋点基线**：会话漏斗、有效会话、反馈、失败、放弃、转人工，落到 `usage/event` 表。
- `PRD-B1` **消息级反馈**：👍/👎 + 原因标签 + 纠错文本，进入 bad case 池（当前无任何反馈能力）。
- `PRD-B2` **会话洞察**：未解决问题聚成主题、高频问题、用户在哪一步放弃。
- `PRD-B3` **bad case → 评测用例**：一键转为评测集用例；真实评测执行器与版本对比面板（消费 backlog P1-6）。
- `PRD-B4` **知识缺口回收**：检索未命中 / 低分问题 → 建议补文档或 FAQ，知识库页面可见。

验收参考：每周能从反馈中产出 ≥ 10 条可行动改进，并能在下一版本验证效果。

### 主题 C：出现在用户工作的地方（分发）

为什么：内部工具的成败常常不在能力，而在"有没有走到用户面前"。

- `PRD-C1` **开放平台**：API Key 真正可用于鉴权，`/open/v1/chat` 最小端点 + OpenAPI 文档（承接 backlog P1-12）。
- `PRD-C2` **嵌入与分享**：iframe / JS 挂件、智能体分享链接与二维码、带配额的访客模式。
- `PRD-C3` **IM 渠道**：企业微信 / 钉钉 / 飞书机器人，与门户会话互通。
- `PRD-C4` **主动式 Agent**：定时简报、告警事件触发分析并推送（复用工作流 TIMER / NOTIFY 能力，产品化成"订阅"）。

验收参考：非平台用户无需账号，通过一个链接或群机器人完成一次完整问答。

### 主题 D：企业信任（治理）

- `PRD-D1` **用户与租户**：注册/邀请、部门、按用户与部门授权智能体和知识库（承接 backlog P1-8）。
- `PRD-D2` **内容安全**：输入输出审核、敏感词、PII 脱敏与留痕。
- `PRD-D3` **成本归属**：用量按用户 / 部门 / 智能体计量，预算、超额策略与账单导出（承接 P1-5）。
- `PRD-D4` **引用与置信**：引用可定位到原文段落、低置信拒答与转人工入口（引用已有，定位与置信缺失）。

验收参考：安全与权限评审可过；一张账单能回答"谁在花多少钱"。

### 主题 E：降低搭建成本（构建者体验）

- `PRD-E1` **从文档/对话生成智能体草稿**（NL2Agent），人工确认后入库。
- `PRD-E2` **提示词版本管理与并排对比调试**。
- `PRD-E3` **模板中心**：客服、知识问答、数据分析、审批助手 4 个内置模板，一键复制。
- `PRD-E4` **知识库质检**：分块预览、命中调试、文档覆盖率与缺口报告。
- `PRD-E5` **工作流调试器**：单步执行、断点、变量查看、节点试运行。

验收参考：新同事 30 分钟内从模板搭出一个可用智能体。

### 主题 F：记忆与个性化（中长期）

- 用户级长期记忆（偏好、常用对象），用户可查看与清除。
- 角色化回答（按部门 / 职级调整口径）。
- 多智能体协作：主管 Agent 调度子 Agent，把工作流能力产品化。

## 5. 下一轮建议：知识问答闭环 v1

**主线目标**：让"问了没答好"的问题能被看见、被归因、被补上，并且下一版能验证确实变好。以下需求是主题 B/D/E 在知识问答场景下的切片。

1. `KQ-1` **回答反馈与无答案识别**（PRD-B1）：消息级 👍/👎/"没解决" + 原因标签；低置信或检索无命中时明确拒答，并提供反馈或找知识运营的入口。验收：负反馈与无答案都能落库，管理端可按智能体、问题聚合。**PRD 已完成：[KQ-1-feedback-and-no-answer.md](prd/KQ-1-feedback-and-no-answer.md)**
2. `KQ-2` **知识缺口看板**（PRD-B2/B4）：未命中、低分、负反馈问题聚类成主题，关联文档缺口，可指派给知识运营并跟踪关闭。验收：每周产出 Top10 缺口清单；补齐文档后同类问题下降可验证。
3. `KQ-3` **引用可信化**（PRD-D4）：引用展示文档名、版本与更新时间、章节或页码，点击定位原文；文档更新后旧引用标记失效。验收：任意答案的引用能在两次点击内看到原文对应段落。
4. `KQ-4` **真实评测与回归**（PRD-B3，承接 backlog P1-6）：bad case 一键入评测集；评测执行器跑真实检索与回答质量评分（Recall@10、nDCG@10 + LLM-as-judge），发布页展示版本对比并作为门禁。验收：同一评测集两次运行结果可复现，门禁基于真实分数。
5. `KQ-5` **文档治理最小版**（PRD-E4/P1-11）：文档负责人、生效与过期时间、过期提醒；分块预览与检索命中调试。验收：过期文档在使用时被标注；分块问题能定位到具体文档。

前置与配套：`PRD-B0` 产品埋点、`PRD-A1` 用户端会话管理（否则员工翻不到上次问答）。

执行顺序：KQ-1 → KQ-2 → KQ-3，与 KQ-4/KQ-5 并行；每完成一项就更新本文档的复盘记录。

本轮明确不做：开放 API、模板中心、IM 渠道、MCP OAuth、多租户计费、多模态文档——留到知识问答闭环跑通后，再按数据决定下一个场景。

## 7. 已确认（2026-11-17）

- **定位**：两者兼顾——用真实产品标准设计，每轮保证一条可演示、可讲述的完整业务闭环。
- **节奏**：每两周一次产品复盘，约每月 1 日与 15 日由定时任务触发；也可随时手动发起。
- **首个场景**：内部知识问答（2026-11-17 确认），定义、指标与闭环见 3.5 节，执行计划见第 5 节。
- **待评审**：点赞是否也要求原因（PRD 当前设计为可选）；`VIEWER` 是否能看到反馈列表（当前设计为不可见）；严格模式拒答文案是否需要按智能体可配（当前固定）。
